> [English version](./working-with-ai-research-workflow.en.md)

AI 能收集案例、查询数据、运行分析、整理结果。研究者仍需要提出值得验证的问题，确认数据定义，判断证据能支持什么结论。把这种协作做顺，关键在于三件事：**分清职责、让上下文可检索、让修正真正进入下一次工作。**

## 1. 从一个假设走到证据

设想一个常见研究场景：模型结果没有达到预期，我们怀疑某种样本分布或行为变化可能解释它。

可以将调查拆成一条明确的路径：

1. **提出假设。** 先说清要解释的现象，以及哪些观察能支持或削弱这个解释。
2. **核对定义。** 确定样本筛选条件、时间窗口、关联字段和指标分母。
3. **收集两类证据。** 一边查看具体案例，一边查询总体样本分布。
4. **扩大验证范围。** 检查发现是否只出现在某一天或某个小样本中。
5. **解释意外结果。** 当两个比例看起来矛盾时，先检查它们统计的对象和分母。
6. **形成有边界的结论。** 区分已观察到的事实、合理解释和仍需验证的问题。

在这条路径上，人负责方向和判断，AI 负责有边界的执行。遇到异常数字时，双方一起回到定义与原始证据，而不是直接把结果包装成结论。

例如，“某类对象占全部对象的比例”和“这类对象贡献的样本占全部样本的比例”可以相差很大：不同对象贡献的样本数可能不同。这里需要解释统计口径，不能仅凭两个百分比推断分析错误或发现了因果关系。

## 2. 分工：Secretary、Lead 和 Worker

把讨论、执行、进度管理全部放进一个对话，会同时增加两端的负担。Agent 的上下文有限；人也需要不停翻聊天记录，确认谁在做什么、哪些结果已经可以使用。

原分享采用三层职责：

| 角色         | 负责什么                               | 交付什么                         |
| ------------ | -------------------------------------- | -------------------------------- |
| Secretary    | 跨项目的优先级、进度与零散事项         | 总体工作安排和需要关注的事项     |
| Project Lead | 一个项目的研究讨论、任务拆分与结果汇总 | 连贯的项目状态、证据与下一步建议 |
| Worker       | 一个范围明确的子任务                   | 结果、证据、限制和未解决问题     |

![Secretary、Project Lead 与 Worker 的职责和汇报关系](./assets/working-with-ai/task-ownership.png)

人的主要研究讨论保留在 Lead 所在的对话里。需要澄清细节时，可以直接与 Worker 沟通，再由 Lead 汇总项目结论。每个角色只保留与职责相关的上下文。

对应到前面的研究问题，Secretary 可以协助确定优先级，Lead 与人一起制定调查方案，Worker 分别做案例分析和样本查询，最后由 Lead 汇合证据，人决定接下来验证什么。

侧栏命名也应体现职责与状态，例如：

```text
Secretary
[Project A] Lead | Research question
[Project A] W01 | Case review (RUNNING)
[Project A] W02 | Sample analysis (REVIEW LEAD)
```

这是一种组织方式，可以从一个项目开始使用。角色的价值在于责任清楚、交接完整；增加角色本身不会自动提高研究质量。

## 3. 记忆：把背景、经历与方法分开保存

长期项目中，很多时间消耗在重复解释：某个标签是什么意思，之前为什么放弃一个方案，脚本应该怎样运行。如果这些知识只散落在聊天里，新任务很容易遗漏关键条件。

原分享借用 [LangChain 对 Agent Memory 的分类](https://www.langchain.com/blog/memory-for-agents)，将上下文分成三类：

| 类型                          | 回答的问题                     | 适合保存的内容                     |
| ----------------------------- | ------------------------------ | ---------------------------------- |
| Semantic Memory，语义记忆     | 这个项目和数据是什么？         | 项目目标、术语、样本与指标定义     |
| Episodic Memory，情景记忆     | 我们做过什么，为什么这样决定？ | 实验过程、调查记录、结果与决策理由 |
| Procedural Memory，程序性记忆 | 这件事应该怎样做？             | Skill、脚本、操作步骤与参考资料    |

比如，一个数据集可能先筛选 T0 当天的交互，再关联 T1 当天的结果标签。新 Agent 必须知道具体筛选条件、时间边界和关联方式，仅知道指标缩写是不够的。

### 一个可复用的项目目录

```text
<project>
├── AGENTS.md
├── CURRENT.md                   当前状态：进入项目时先读
├── context/                     语义记忆
│   ├── AGENTS.md
│   ├── INDEX.md
│   └── <topic>.md
├── experiments/                 情景记忆：实验生命周期
│   ├── AGENTS.md
│   ├── model-training/
│   │   ├── INDEX.md
│   │   └── <version>/
│   └── ab-testing/
│       └── INDEX.md
├── studies/                     情景记忆：围绕问题的专项调查
│   ├── AGENTS.md
│   ├── INDEX.md
│   └── <study>/
└── workflow/                    程序性记忆
    ├── AGENTS.md
    └── <procedure>/
        ├── SKILL.md
        ├── scripts/
        └── references/
```

**写入时**，每个目录的 `AGENTS.md` 说明哪些内容放在这里、怎样记录、如何维护索引。

**读取时**，先看 `CURRENT.md`，了解当前状态、主要阻碍和下一项决策，再按需从索引进入定义、实验记录或操作流程。

一次调查可以这样贯穿目录：先从 `context/` 查样本定义，从 `experiments/` 找需要比较的实验，再从 `workflow/` 找案例收集流程，最后把发现写入 `studies/` 并更新索引。下一次任务就有了可追溯的入口。

## 4. 持续改进：修复问题，也整理累积的规则

纠正一次错误，只解决了当前任务的一部分。如果每次修正都追加一条提示，长期下来又会出现新的问题：规则重复、要求冲突、过时检查越来越多。

原分享把改进拆成两个相互连接的循环。

![两个改进循环：发现问题后修复验证，定期合并并简化指导](./assets/working-with-ai/workflow-improvement.svg)

### 循环一：问题出现时修复

执行任务 → 发现问题 → 修正相关代码或 Skill → 检查修复及既有行为。

例如，Agent 误解了一个样本定义。纠正后，应把准确口径补入对应的知识或操作文件，让未来任务能够查到，而不只是留在当前聊天中。

### 循环二：定期整理累积的修正

回顾近期修正 → 找出重复或过时指导 → 合并与简化 → 验证简化后的行为。

Hook 可以在收到反馈时启动修复流程；定时任务可以启动周期性整理。人仍然判断问题是否成立、修复是否合适，自动化负责减少安排后续步骤的重复劳动。

**一次修复应该帮助下一次任务，定期整理则让这些帮助仍然容易找到。**

## 5. 日常使用中的几个技巧

### 用语音，但区分两种节奏

**语音输入**适合先完整表达，再阅读识别结果、修改并发送。它保留了一轮一轮交流的节奏，适合中间需要安静思考的任务。

**实时语音对话**适合边讨论边执行：快速反馈、分派工作，或在任务进行中调整方向。原分享推荐的延伸阅读是 [Voice Agent as an Event Loop](https://steventan0110.github.io/blog/2026/voice-agent-as-an-event-loop/)。

如果语音工具支持自定义词典，可以保存经常识别错误的人名与技术术语，并确认修正确实保存。长时间思考时，也可以切回普通语音输入。

### 在支持远程访问的环境里查看进度

离开桌面后，用手机查看进度、补充一条指令，能减少工作中断。具体能力取决于所用工具与配置；持续在线也应保留自己的工作边界。

### 优先使用 CLI，再考虑 API 和浏览器 DOM

有官方 CLI 时先使用 CLI；没有合适命令时，寻找受支持的 API；最后再用浏览器 DOM 自动化。

结构化接口通常更适合批量操作，也较少受到页面布局变化影响。无论采用哪种接口，都需要核对返回内容与实际结果。

### 将例行工作放进可检查的循环

[Loop Engineering](https://addyosmani.com/blog/loop-engineering/) 是原分享推荐的相关阅读。对于目标明确、结果可检查的例行任务，可以建立执行与检查循环。

例如监控任务可以约定：正常时保持安静，出现需要处理的问题时才通知。研究方向、数据口径和结论解释仍在变化时，应继续保留人的判断。

## 6. 如何理解投入与 Token 的统计图

![一周案例中，不同工作类别的人类投入占比与关联 Token 占比](./assets/working-with-ai/human-input-and-tokens.png)

这张原图展示一个星期的工作分类统计，但左右两侧的分母不同：

- **Human Input Share**：某类加权工作输入占全部工作输入的比例。
- **Associated Token Share**：按单一目标归属统计的关联 Token 占全部观察到的 Token 的比例。

因此，不能把右侧百分比除以左侧百分比，就说 AI 带来了多少倍效率提升。它不是受控的生产力实验，Token 消耗也不等于研究产出或业务价值。

这张图更适合用来反思分工：人的输入分布在哪些环节？执行和基础设施维护消耗了多少计算？是否把足够注意力留给了问题定义、证据检查与最终交付？

## 7. 从一个真实任务开始

原分享最后强调三件事：

- **把范围明确的工作交给 AI。** 自己参与决策、核对证据，并保存下一次任务需要的背景。
- **持续学习与练习。** 技术博客适合深入理解；演示适合照着试；访谈和播客提供经验与背景；开发者的公开记录有助于发现新方法。
- **围绕自己的工作建立 Agent。** 从一个在意的任务出发，在使用中逐步完善流程。

原分享还推荐了 [Tidemark 阅读摘要](https://harry20030331.github.io/tidemark/) 及其所参考的 [Follow Builders](https://github.com/zarazhangrui/follow-builders)。摘要可以作为发现材料的入口，遇到重要论点，再回到原始来源。

一个合适的起点是：选一个正在推进的研究问题，写清定义、分派一个有边界的子任务、检查返回的证据，再把这次真正有用的经验存回项目。
